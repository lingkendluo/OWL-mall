CHAPTER 01前端开发（阶段一）

前端阶段的目标不是"画完所有页面"，而是跑通一条可演示的主链路 + 产出一份可执行的接口契约。前者让你能给评审演示，后者让后端不必猜。按这个标准，前端阶段的实际交付物是：1 个可运行的 Web 工程（B 端后台后置）、1 份 openapi.yaml、1 套 Mock 数据、1 条 E2E 用例。

为什么这一期只做 Web，为什么不做多端

多端复用听起来很美，但它的成本集中在差异处：条件编译分支、平台专有 API（登录、支付、文件、路由栈）、真机调试、以及小程序 2MB 主包带来的分包切分。这些成本全在一期就付，而收益要等到小程序上线才兑现。一期的真实风险不是"端不够多"，而是主链路迟迟跑不通。所以策略是：先用 Vue 3 单工程把 H5 做到可演示，把不确定性压缩在业务逻辑与契约上；小程序作为第二阶段，用同一套 stores / api / utils 迁移，只重写视图层与平台适配层。届时若确实需要多端，再评估是否引入 uni-app，而不是现在就把整个工程押在一个跨端框架上。

Web 端需要额外注意的两件事（相比小程序）

① 登录态：没有微信授权登录，一期只做「手机号 + 密码」与「短信验证码」两种；token 存 localStorage，因此必须防 XSS（不用 v-html 渲染用户内容）。
② 支付：没有 JSAPI，一期用模拟支付（Mock 收银台直接回调成功），二期接 H5 支付或扫码支付。

1.5状态管理与数据层

1.5.1 Store 划分原则

只把跨页面存活且服务端无唯一真相的数据放进 Pinia。商品详情这类"每次进来都要新鲜"的数据不进 store，直接页面内请求——否则会出现"从缓存进入详情页看到的是昨天的价格"。

Store持有状态持久化
useUserStoretoken、refreshToken、用户信息、会员等级、是否实名localStorage（token 单独 key，不放 Pinia 持久化里；不存敏感明文）
useCartStore购物车条目、选中的 SKU id 集合、按店铺分组后的计算属性不持久化，以服务端为准；离线加购走本地队列
useAddressStore地址列表、默认地址、本次结算选中的地址仅缓存 defaultId
useAppStore系统信息、安全区、主题、灰度开关、未读消息数会话级

1.5.2 请求层封装

请求层要解决 4 件事：统一响应解包、Token 自动刷新（并发只刷一次）、错误码到用户话术的映射、TraceId 透传（排障时能直接拿给后端）。

// src/utils/request.ts —— axios 版请求层
import axios, { type AxiosRequestConfig } from 'axios'
import { useUserStore } from '@/stores/user'
import { toast } from '@/utils/ui'
import { ERROR_TEXT } from '@/types/error-code'

export interface ApiResp<T> {
  code: number; message: string; data: T; traceId: string
}

const http = axios.create({
  baseURL: import.meta.env.VITE_API_BASE,
  timeout: 15000,
})
let refreshing: Promise<void> | null = null   // 刷新单飞，避免并发刷新互相覆盖

export async function request<T>(
  config: AxiosRequestConfig & { auth?: boolean; silent?: boolean },
  retried = false
): Promise<T> {
  const user = useUserStore()
  const { auth, silent, ...rest } = config

  const res = await http.request<ApiResp<T>>({
    ...rest,
    headers: auth !== false && user.accessToken
      ? { Authorization: `Bearer ${user.accessToken}` }
      : {},
    validateStatus: () => true,   // HTTP 状态码交给下面统一判断
  })
  const body = res.data

  // 401：Token 过期，刷新后重放一次（只重放一次，防死循环）
  if (res.status === 401 && !retried) {
    if (!refreshing) {
      refreshing = user.refreshToken()
        .finally(() => { refreshing = null })
    }
    await refreshing
    return request<T>(config, true)
  }

  if (res.status >= 500) {
    if (!silent) toast('服务开小差了，请稍后重试')
    throw new Error(`HTTP_${res.status}`)
  }

  if (body.code !== 0) {
    // 业务错误：优先用后端 message，缺失则查错误码字典兜底
    const msg = body.message || ERROR_TEXT[body.code] || '操作失败'
    if (!silent) toast(msg)
    // 把 traceId 挂到错误上，便于用户截图反馈时定位
    const err = new Error(msg) as Error & { code: number; traceId: string }
    err.code = body.code; err.traceId = body.traceId
    throw err
  }
  return body.data
}
为什么用 axios 而不是 fetch

不是技术偏好问题，是成本：axios 自带超时、取消（AbortController 的封装）、请求/响应拦截器、baseURL，这几样在 fetch 上都要自己写一遍，而它们正好是请求层最容易被写漏的部分。若团队已有 fetch 封装，把上面的 http.request 换成 fetch(BASE + url) 即可，其余逻辑（单飞、错误码、traceId）一行不用改。

登录态的三个陷阱

① 刷新风暴：页面同时发 5 个请求全部 401，若每个都去刷新 Token，会导致 refreshToken 被重复使用而失效。必须用单飞（前文的 refreshing 变量）。
② 刷新后死循环：刷新接口本身 401 时必须直接跳登录页，不能再走重试。
③ 静默请求：首页推荐位这类"失败也不该打扰用户"的请求，要支持 silent: true。

1.6.2 SKU 选择器：前端最值得写对的组件

规格选择的核心难点不是"渲染按钮"，而是可选路径判定：用户选了"红色 + L"，那么"蓝色"是否应该置灰？答案取决于"蓝色是否还存在有库存的 SKU 组合"。用"笛卡尔积 + 逐项试算"可以稳定解决。

// src/components/sku-picker/useSku.ts
export interface Sku {
  id: string
  specs: Record<string, string>   // { 颜色: '红', 尺码: 'L' }
  price: number                    // 单位：分
  stock: number
}

/** 判断：在当前已选条件下，把 specKey 选为 specValue 是否还有可售 SKU */
export function canSelect(
  skus: Sku[],
  selected: Record<string, string>,
  specKey: string,
  specValue: string
): boolean {
  const probe = { ...selected, [specKey]: specValue }
  return skus.some(sku =>
    sku.stock > 0 &&
    Object.entries(probe).every(([k, v]) => sku.specs[k] === v)
  )
}

/** 已选规格是否能唯一确定一个 SKU */
export function matchSku(skus: Sku[], selected: Record<string, string>) {
  return skus.find(sku =>
    Object.keys(sku.specs).length === Object.keys(selected).length &&
    Object.entries(selected).every(([k, v]) => sku.specs[k] === v)
  )
}
这个 20 行函数的三个易错点

① 不能用"当前 SKU 的库存"判断：置灰要按整个 SKU 列表判定，否则会出现"选了红色后，明明有货的 L 码被置灰"。
② 切换规格要清理失效选择：从"红/L"切到"蓝"时，若蓝没有 L，应自动清空尺码而不是报错。
③ 价格显示区间：未选全规格时显示 ¥99 起（取最小价），选全后显示精确价。

1.7关键页面实现要点

页面实现要点（踩过的坑）
首页首屏必须"可缓存渲染"：Banner/金刚区/楼层用骨架屏占位，数据到达后替换。滚动到第 2 屏再加载推荐位。不要等所有接口返回再渲染白屏 1.5 秒

收银台调起支付前先查单（防止已支付重复支付）；支付完成后不信任前端回调结果，轮询 /payments/{no} 最多 10 次（1s/2s/3s 递增）；超时则提示"支付结果确认中"并跳订单详情

CHAPTER 02后端开发（阶段二）

后端的任务不是"实现接口"，而是守住边界。整个系统有 38 个 C 端接口、50 余个 B 端接口，如果全部堆在 Service 里，三个月后没人敢改价格逻辑。所以下面的顺序是：先划模块（2.1）、再定分层（2.2-2.3）、再建模（2.4-2.5），最后才是链路（2.6-2.12）。

包放什么禁止放什么（违反即架构劣化）

interfaces.requestHTTP 请求体、@NotNull/@Min 等校验注解与数据库字段强耦合的"万能 Request"；一个 Request 服务多个接口

application.listener订阅其他模块的领域事件，转成本模块的用例调用在监听器里写业务逻辑；直接改别人模块的表
domain.model聚合根、实体、值对象、状态枚举与迁移规则Spring 注解（除 @Component 于领域服务）、MyBatis 注解、HttpServletRequest
domain.service跨实体/跨聚合的规则，如拆单、计价、库存分配策略事务控制、远程调用、缓存读写
domain.repository仓储接口，方法签名用领域语言（findByNo、save）实现类、SQL、QueryWrapper 这类 MyBatis-Plus 对象
domain.event领域事件（不可变），只描述"发生了什么"携带大量数据（事件要小，需要详情让消费方回查）
infrastructure.persistenceMapper、PO、仓储实现、PO↔Domain 转换业务规则；被 domain 反向引用
infrastructure.cache缓存读写、key 规划、序列化把缓存当唯一数据源
infrastructure.mq生产者（发事件）、消费者（幂等 + 转调 application）消费者里直接操作 DB；无幂等键的消费
infrastructure.client调用其他模块 API 的适配器，负责重试、超时、降级、DTO 转换直接 import 对方 domain 包；把对方 DTO 直接返回给前端

2.3系统架构

2.4核心领域模型

只画 4 个聚合：Spu（商品）、Order（订单）、Payment（支付）、Inventory（库存）。其余实体围绕它们展开。聚合的判定标准是事务一致性边界——一次操作必须同时改完的，才放进同一个聚合。

三个建模决策值得说明

① 为什么不把 Inventory 放进 Sku 聚合？因为库存是高频写、商品是低频写。放一起意味着每次扣库存都要锁商品行，商品编辑和下单会互相阻塞。
② 为什么 Order 只存 addressSnapshot 而不外键关联 Address？地址会被用户修改或删除，但订单必须保留下单当时的收货信息——这是法律凭证要求。
③ 为什么 Payment 独立成聚合？支付单的状态由第三方渠道驱动，与订单状态机节奏不同（订单可能已关闭但支付渠道仍在处理）。分开放，才能处理"多付/重复支付"的退款。

不要用异常做流程控制

"库存不足"这种预期内的业务分支，应该在下单流程里返回明确的结果对象（如 StockLockResult.fail(skuId, available)），而不是抛异常。异常只用于"不该发生"的情况。否则链路里充斥着 try-catch，性能与可读性双输。

下单是整个系统最复杂的 200 毫秒。它要在一个事务里协调库存、优惠、订单三件事，还要保证重试不重复、失败可补偿。下面这张时序图是实现说明书——每一根线都对应一个方法调用。

2.7.1 关键代码：库存预扣

// owl-inventory/.../StockServiceImpl.java
private static final String LUA_DEDUCT = """
  local key    = KEYS[1]
  local qty    = tonumber(ARGV[1])
  local avail  = tonumber(redis.call('HGET', key, 'available') or '-1')
  if avail < 0 then return -2 end          -- 缓存未预热
  if avail < qty then return avail end     -- 库存不足，返回剩余量
  redis.call('HINCRBY', key, 'available', -qty)
  redis.call('HINCRBY', key, 'locked', qty)
  return avail - qty
""";

@Override
public StockLockResult tryLock(Long skuId, int qty) {
    String key = "stock:" + skuId;
    Long remain = redis.execute(new DefaultRedisScript<>(LUA_DEDUCT, Long.class),
                                List.of(key), String.valueOf(qty));
    if (remain == null) throw new BizException(ErrorCode.SYSTEM_BUSY);
    if (remain == -2) return loadAndRetry(skuId, qty);   // 回源 DB 预热后重试
    if (remain < 0)   return StockLockResult.fail(skuId, remain + qty);
    // 记录流水，供异步落库与对账使用
    stockFlowRepo.append(skuId, -qty, StockFlowType.LOCK);
    return StockLockResult.ok(remain);
}
为什么用 Lua 而不是分布式锁

分布式锁（Redisson）做"扣库存"需要 加锁 → 读 → 判断 → 写 → 解锁 五次网络往返，单次 5-10ms；Lua 脚本一次往返 1-2ms，且天然原子。在 TPS 1000 的场景下，这个差距是"能不能扛住"的区别。锁适合"保护临界区里的复杂逻辑"，不适合"单一的计数递减"。

2.8订单状态机

订单状态必须收敛到一个枚举 + 一张迁移表，所有状态变更走同一个方法 order.transitTo(target, reason)，由它校验合法性。散落在各处的 if (status == 20) order.setStatus(30) 是线上事故的主要来源。

// 状态迁移表：只允许表中出现的路径，其余一律抛 ORDER_STATUS_ILLEGAL
private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
    PENDING_PAYMENT, Set.of(PAID, CANCELLED),
    PAID,            Set.of(SHIPPED, REFUNDED, AFTER_SALE),
    SHIPPED,         Set.of(COMPLETED, AFTER_SALE),
    COMPLETED,       Set.of(AFTER_SALE),
    AFTER_SALE,      Set.of(REFUNDED, COMPLETED),
    CANCELLED,       Set.of(),
    REFUNDED,        Set.of()
);

public void transitTo(OrderStatus target, String reason) {
    if (!ALLOWED.get(this.status).contains(target)) {
        throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL,
            "订单 %s 不能从 %s 变更为 %s".formatted(orderNo, status, target));
    }
    OrderStatus from = this.status;
    this.status = target;
    registerEvent(new OrderStatusChanged(orderNo, from, target, reason, Instant.now()));
}

2.9支付与对账

支付模块的设计目标只有两个：不错账、不丢单。前者靠对账，后者靠回调 + 主动查单双保险。渠道差异（微信/支付宝/数币）用策略模式隔离，业务层只认统一接口。

2.9.1 支付单状态机

状态触发处理要点
INIT 已创建用户点击支付生成 payNo，调渠道下单接口，拿到 prepayId/payUrl
PAYING 支付中渠道返回预支付成功前端调起收银台；服务端开始轮询窗口（5 分钟内每 30s 查一次）
SUCCESS 已支付回调验签通过 / 主动查单成功发 PaymentSucceeded，驱动订单转 PAID；幂等更新
FAILED 失败渠道返回失败允许用户重新发起，复用同一 orderNo，新建 payNo
CLOSED 已关闭订单取消 / 超时调渠道关单接口，避免用户"关单后仍能支付"
REFUNDING/REFUNDED退款申请 / 退款完成退款单独立幂等键 refundNo；部分退款累加校验

2.9.2 回调处理骨架

@PostMapping("/notify/{channel}")
public String notify(@PathVariable String channel,
                     @RequestBody String rawBody,
                     @RequestHeader Map<String, String> headers) {

    PayChannelStrategy strategy = strategyFactory.get(channel);

    // 1. 验签：必须用原始报文，不能用反序列化后的对象
    if (!strategy.verifySign(rawBody, headers)) {
        log.warn("pay notify sign invalid, channel={}", channel);
        return strategy.failReply();
    }

    PayNotify notify = strategy.parse(rawBody);

    // 2. 幂等：同一 out_trade_no 的重复通知直接返回成功
    if (payNotifyLogRepo.exists(notify.getOutTradeNo())) {
        return strategy.successReply();
    }

    // 3. 金额二次校验：防止渠道金额被篡改
    Payment payment = paymentRepo.findByPayNo(notify.getPayNo());
    if (!payment.getAmount().equals(notify.getAmount())) {
        log.error("amount mismatch payNo={} expect={} actual={}",
                  payment.getPayNo(), payment.getAmount(), notify.getAmount());
        return strategy.failReply();
    }

    // 4. 只落事件，业务异步处理：保证回调 100ms 内返回，避免渠道重试风暴
    outboxRepo.append(new PaymentSucceeded(payment.getPayNo(), notify.getChannelTradeNo()));
    return strategy.successReply();
}

// 定时补偿：每 5 分钟扫描 PAYING 超过 2 分钟的单，主动查单
@Scheduled(cron = "0 */5 * * * ?")
public void reconcilePaying() {
    paymentRepo.findStalePaying(Duration.ofMinutes(2))
        .forEach(p -> strategyFactory.get(p.getChannel()).queryAndSync(p));
}
支付模块的三条红线

① 回调必须验签，且用原始 body；② 金额必须二次校验，绝不信任回调里的金额直接改订单；③ 回调要快速返回，业务处理全部异步——微信回调超时 5 秒会重试 8 次，同步处理重业务必然雪崩。

2.10库存与秒杀

库存的核心矛盾是：DB 行锁撑不住 1000 TPS，纯 Redis 又会丢数据。解法是"Redis 决策、DB 记账、流水对账"三层结构。

层职责一致性
Redis实时可售库存、原子扣减、限购标记强一致（Lua 原子），是下单时的唯一判断依据
库存流水每次锁定/释放/扣减记一条流水（MQ 异步落库）最终一致，用于回溯与对账
MySQLinventory_stock 的 total/locked/sold 记账异步更新，每小时与 Redis 对账一次
兜底DB 侧 UPDATE ... WHERE available >= qty 乐观锁即使 Redis 挂了也不超卖，只是性能降级

2.10.1 秒杀五道闸门

#闸门实现拦住的量级
1页面静态化活动页 CDN 缓存，倒计时用服务端时间校准；按钮置灰由前端根据接口状态控制90% 的浏览流量不进服务
2网关限流Sentinel 热点参数限流：userId 维度 5 次/秒，activityId 维度总入口 QPS 上限刷接口的脚本
3资格校验Redis Set 存已购用户（seckill:buyers:{activityId}），重复抢购直接拒重复提交
4Redis 原子扣减Lua：判断库存 → 扣减 → 写购买标记，一次往返超卖
5MQ 削峰扣减成功即返回"排队中"，异步消费建单，消费者按能力匀速拉取DB 写压力
 
// 秒杀 Lua：库存 + 一人一单 在同一个脚本里完成，避免两次往返产生的竞态
private static final String SECKILL_LUA = """
  local stockKey  = KEYS[1]        -- seckill:stock:{activityId}
  local buyerKey  = KEYS[2]        -- seckill:buyers:{activityId}
  local userId    = ARGV[1]
  local qty       = tonumber(ARGV[2])

  if redis.call('SISMEMBER', buyerKey, userId) == 1 then return -1 end   -- 已购
  local stock = tonumber(redis.call('GET', stockKey) or '0')
  if stock < qty then return -2 end                                      -- 售罄
  redis.call('DECRBY', stockKey, qty)
  redis.call('SADD', buyerKey, userId)
  return stock - qty
""";
秒杀最容易被忽略的一步：回补

用户抢到但 15 分钟未支付，必须同时做三件事：Redis 库存 +1、从 buyers 集合移除该用户、关闭订单。少做一步就会出现"库存有货但用户买不了"或"同一用户重复抢"。回补逻辑要幂等——延时消息可能重复投递。

2.11缓存设计

缓存不是"加个 Redis 就快了"，而是一套分层策略 + 一套失效协议。本项目采用 L1（Caffeine，进程内，毫秒级）+ L2（Redis，集群，网络级）两级。

数据L1L2失效策略
类目树 / 属性模板10 min1 h后台修改后发广播事件，各节点清 L1
商品详情（基础信息）5 s10 min商品更新发 ItemUpdated，删 L2 + 广播删 L1
SKU 价格—5 min改价后立即删；大促期间缩短至 30s
库存不走缓存读，直接读 Redis 计数（本身即缓存）写时更新
首页楼层 / Banner30 s5 min运营配置变更后主动刷新
用户会话—30 min 滑动过期登出即删

2.11.1 三个经典问题

问题场景对策
穿透查询不存在的 ID，请求全打到 DB① 空值缓存 60s（值存 __NULL__）；② 布隆过滤器预判商品 ID 是否存在；③ 参数合法性校验（ID ≤ 0 直接拒）
击穿热点 key 过期瞬间，大量请求同时回源① 逻辑过期（value 内存过期时间，异步重建）；② 重建时加分布式锁，未抢到的等待 50ms 后重读；③ 热点 key 永不过期 + 后台刷新
雪崩大量 key 同时失效 / Redis 整体不可用① 过期时间加随机抖动 ±10%；② Redis Cluster 多副本；③ 降级：直接读 DB 并限流，或返回静态兜底页

2.11.2 缓存一致性

// 更新策略：先更 DB，再删缓存（Cache Aside），并延迟双删
@Transactional
public void updateItem(ItemUpdateCmd cmd) {
    itemRepo.update(cmd);                       // 1. 写库
    cache.delete("item:" + cmd.getSpuId());      // 2. 删 L2
    afterCommit(() -> {                          // 3. 提交后广播删 L1
        eventPublisher.publish(new CacheEvictEvent("item", cmd.getSpuId()));
        scheduleAfter(500, () -> cache.delete("item:" + cmd.getSpuId())); // 4. 延迟再删一次
    });
}
为什么"先删缓存再写库"是错的

先删缓存 → 另一个请求读缓存未命中 → 读到旧 DB 值 → 写回缓存 → 你的写库才完成。此时缓存里是旧值，且长期有效。正确顺序是先写库、后删缓存；延迟双删是为了覆盖"删缓存瞬间有读请求把旧值写回"的极端窗口。
